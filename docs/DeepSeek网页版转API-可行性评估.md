# DeepSeek 网页版 → OpenAI 兼容 API：可行性与开发成本评估

> 评估日期：2026-10-02
> 参照物：`~/.iskill-headroom-workbuddy/workbuddy2api-hub`（下文简称 hub，Python，~13,000 行）
> 目标：把 `chat.deepseek.com` 封装成 OpenAI 兼容 API，**供 agent 客户端调用**

---

## 一、结论先行

| 维度 | 判断 |
|---|---|
| **技术可行性** | ✅ **可行**。已有多个活跃先例证明纯 HTTP 反代路线能跑通，不是死路 |
| **与"agent 客户端"的匹配度** | ❌ **严重错配**。工具调用是 prompt 模拟的，限流与封号会让 agent 循环随时中断 |
| **从 hub fork 的性价比** | ⚠️ **被高估**。能复用的是周边设施，核心难点全部要新写 |
| **经济账** | ❌ **不划算**。官方 V4-Pro 缓存未命中 ¥3/M、输出 ¥6/M，套利空间远小于 WorkBuddy 场景 |
| **已有实现** | ✅ **功能已被完整实现**。`ds-free-api`（★770）、`deeperseeker`（★194，MIT）都已做完，**自研无意义** |
| **真正的瓶颈** | ❌ **账号存活，不是功能**。上游风控已收紧到"每账号发 2 次请求也可能 12 小时内被封" |
| **总体建议** | **不要自研，也不要指望它跑 agent**。想验证就用现成的跑一遍，别投入开发工时 |

**一句话**：这不是一个"能不能做出来"的问题，而是一个"做出来之后能不能扛住 agent 负载"的问题。

## 二、三个核心错配（这是本次评估最重要的部分）

### 错配 1：网页端是**有状态**的，OpenAI 协议是**无状态**的

| | OpenAI 协议 | DeepSeek 网页端 |
|---|---|---|
| 上下文来源 | 客户端每次带上完整 `messages` 数组 | 服务端按 `chat_session_id` 保存 |
| 请求体 | `{model, messages, stream}` | `{chat_session_id, prompt, thinking_enabled, search_enabled, model_type}` |
| 语义 | 纯函数，同样输入 → 同样输出 | 追加式会话，受网页端历史裁剪策略约束 |

**后果**：每次请求都要做一次「messages 数组 → 单条 prompt 字符串」的扁平化。这会带来三个连锁问题：

1. **上下文重复计费**：agent 每轮都重发全部历史，而网页端的免费额度是按"消息条数/长度"算的，等于同一段历史被反复消耗额度。
2. **无法复用上游缓存**：hub 的 headroom 层最核心的价值是"冻结历史前缀吃上游 prompt cache（命中价是未命中的 2%）"。网页端不暴露缓存控制，这个杠杆**完全失效**。
3. **工具结果无法回注**：agent 循环里 `role=tool` 的消息是模型没生成过的内容。网页端只接受"用户说的话"，你只能把它伪装成新一轮 user prompt，模型对工具结果的语义理解会明显劣化。

### 错配 2：工具调用 —— 原生 vs **prompt 模拟**

这是对"agent 客户端"场景**最致命**的一条。

- hub 面对的上游 `/v2/chat/completions` **原生吐 OpenAI 风格 SSE**，`delta.tool_calls` 是结构化的，hub 只需 `clean_chunk` 消毒 + `aggregate_stream` 聚合。
- DeepSeek 网页端**完全没有 function calling**。业界做法是：把工具定义注入 prompt → 让模型用文本吐出调用 → 用解析器抓回来 → 转成 `tool_calls`。

成熟项目（DS-Free-API）为此写了一条**三层自修复管线**（文本修复 → JSON 修复 → 模型兜底），覆盖 10+ 种异常格式，还要处理全角 `｜`↔`|`、`▁`↔`_` 之类的幻觉标签。

**为什么这对 agent 致命**：agent 客户端（Cursor / Cline / Claude Code / WorkBuddy 自身）每一个任务会发起**几十次**工具调用。prompt 模拟的工具调用即使做到 98% 准确率，一个 50 步的任务也有 ~64% 概率至少错一次。原生 tool calling 是 99.9%+。这个差距在单轮聊天里无感，在 agent 循环里是**不可用**。

### 错配 3：账号存活率 —— 这是真正的成本项

来自 DS-Free-API（Rust，2026-09-20 最新提交）README 的一手记录：

| 错误码 | 含义 | 可恢复性 |
|---|---|---|
| `biz_code=10 USER_IS_BANNED` | 永久封禁 | ❌ 不可恢复 |
| `biz_code=5 user is muted` | 临时禁言（返回 `mute_until`，通常数周） | ❌ 重新登录也无效 |
| `biz_code=11 RISK_DEVICE_DETECTED` | 缺浏览器设备指纹 | ✅ 补 `device_id` 可解 |

其他关键事实：

- **`device_id` 不可伪造**。它来自数美（Shumei）SDK 的设备指纹，必须**从真实浏览器里取一次**（登录 `chat.deepseek.com/sign_in` 后从 `users/login` 请求体里抄），每个账号要各自独立。伪造的 base64 字符串直接返回 `RISK_DEVICE_DETECTED`。
- **压测实测**：配额内账号 1/2 在约 **27 次请求**后被再次禁言，账号 3 正常（作者标注共享指纹是未排除的混淆因素）。
- 作者明确写：*"这是待验证的缓解，不是已证实的解法"*。
- 上游已**下线 expert / vision 模型**（2026-09），`model_configs` 里只剩 `default` 一个可用。也就是说**你封装的只有一个模型**。

对比 hub 面对的场景：WorkBuddy 内置模型是随桌面端**付费订阅**附带的额度，账号本身就是"你的"，多账号调度是在合法边界内做负载均衡。DeepSeek 网页端的账号池则是**消耗品**——每加一个账号都要一个真实浏览器 + 真实手机号，且寿命可能只有几十次请求。

**结论**：hub 里最值钱的那套"多账号池 + 故障切换"，在 DeepSeek 场景下**输入成本高、输出寿命短**，投入产出比完全不同。

## 三、技术路线选择

| 路线 | 做法 | 优点 | 缺点 | 判断 |
|---|---|---|---|---|
| **A. 纯 HTTP 反代** | 复刻网页端私有协议 + 解 PoW | 快、省资源、可多账号 | 协议改版即失效；需对抗 WAF | ✅ **唯一可行** |
| **B. 浏览器自动化** | Playwright/CDP 驱动真实页面 | 天然带 `device_id` 和 WAF cookie，抗改版稍好 | 慢（秒级）、吃内存、DOM 改版即失效、无法并发 | ⚠️ 仅适合做 `device_id`/cookie 的**取号器**，不做主链路 |
| **C. 混合** | 无头浏览器定期取 `device_id` + cookie，主链路走 HTTP | 兼顾抗风控与性能 | 复杂度最高 | 🔸 若真要做，这是**最终形态** |

**A 路线的关键难点清单**（全部需要新写，hub 里没有对应实现）：

1. **PoW 求解**：`POST /api/v0/chat/create_pow_challenge` 领题 → 解 `DeepSeekHashV1` → 结果 base64 后放进 `x-ds-pow-response` 头。**一次性、300 秒过期**，复用返回 `40301 INVALID_POW_RESPONSE`。
   - 速度差异巨大：纯 Python 暴力 **15–40 秒/条**（windows0041 实测）vs 复用官方 wasm **~0.3 秒**。**必须走 wasm 路线**，否则单条延迟就废了。
2. **device_id 获取**：必须真实浏览器。
3. **SSE 归约**：网页端返回的不是 OpenAI 风格 delta，而是「完整消息对象 + JSON-Patch（`p`/`o`/`v`）+ 裸 `{"v":"str"}` 文本增量 + `event: title/close`」。需要写一个 **JSON-Patch 状态机**把补丁流还原成文本，再重编码成 OpenAI delta。
4. **WAF 对抗**：⚠️ **信源冲突**——DS-Free-API 说桌面 Chrome UA 会被 **AWS WAF 202** 拦截，需伪装成 Android App（补全套 `x-client-version` / `x-platform` / `x-device-id` / `x-bundle-id` 等头）；另有信源称是**腾讯 WAF**，需带 `HWWAFSESID` / `HWWAFSESTIME` cookie。**两者可能都对（分层 WAF），但必须实际抓包确认**，这是动手前第一个要做的验证。
5. **会话生命周期**：`chat_session/create` 建会话、用完销毁。注意 DS-Free-API 明确**故意不复用会话**，因为账号池共享会导致跨用户上下文串台。

## 四、hub 代码能复用多少？—— 逐模块判定

先说一个**反直觉的发现**：hub 之所以"协议转换层很薄"，是因为 **WorkBuddy 上游本身就吐 OpenAI 风格 SSE**，`clean_chunk` 只是"直通 + 消毒"。这个便利在 DeepSeek 场景**完全不存在**。

| 模块 | hub 行数 | 判定 | 理由 |
|---|---|---|---|
| `wb_accounts.AccountPool` / `SessionAffinity` | ~700 | 🟢 **可复用** | `pick` / `ready` / `note_error` / `throttle_wait` / 冷却与退避骨架与上游无关 |
| `open_upstream` 重试与故障切换 | ~160 | 🟢 **可复用** | 429 按模型冷却、401 轮换、5xx 重试的逻辑是通用的 |
| API-Key 鉴权、用量记账、CORS、HTTP 助手 | ~800 | 🟢 **可复用** | 纯网关设施 |
| `dashboard.html` + `wb_settings.py` 面板 | ~700 | 🟢 **可复用** | 账号管理 / 用量 / 设置界面 |
| `wb_scheduler.py` 定时器框架 | 196 | 🟢 **可复用** | 保活、巡检 |
| `tests/` 骨架（24 个用例） | ~4,900 | 🟡 **半复用** | 断言要重写，但目录结构与 `run_all.py` 入口可用 |
| `Account.headers` / `refresh` / `start_login` / `poll_login` | ~200 | 🔴 **需改写** | 路径与凭证格式 WorkBuddy 专属 |
| `wb_identity.py` 身份头 | 145 | 🔴 **需改写** | 换成 DeepSeek 的 `x-*` 全套 App 头 |
| `UPSTREAM` / `CHAT_PATH` / `MODELS_PATH` | 3 | 🔴 **需改写** | 模块级常量，好改 |
| `build_upstream_body` | ~330 | 🔴 **需重写** | 从 `messages` 数组改成 `prompt` 扁平化 |
| `clean_chunk` / `aggregate_stream` | ~230 | 🔴 **需重写** | 上游格式完全不同 |
| `wb_catalog.py` 模型目录 | 1,731 | ⚫ **作废** | DeepSeek 网页端只剩 1 个模型 |
| `wb_tasks.py` 成长任务/签到 | 633 | ⚫ **作废** | WorkBuddy 国内版专属 |
| — | — | 🔵 **需新增** | **PoW 求解器、device_id 取号器、JSON-Patch SSE 归约器、prompt-based 工具调用 + 解析修复管线、DeepSeek 会话生命周期** |

### 关键结论

> **⚠️ hub 里没有可插拔的「上游适配层」。** 全仓搜不到任何 `Adapter` / `Provider` / `Backend` 抽象类。所谓多上游只是 `get_realm_config(realm)` 返回 `{domain, ...}` 的**同厂商多区域**抽象，不是**多厂商**抽象。上游耦合是**硬编码**在 `wb_proxy.py`（7,239 行单文件）里的。

这意味着 fork hub = 在一个 7,239 行的单文件里做**外科手术式改造**，而不是"写一个新 adapter 插件"。改造过程中你还要持续跟进 hub 上游的更新，**合并冲突会长期存在**。

**量化**：hub 的 ~13,000 行里，约 **60% 是通用网关设施**（可复用），但**核心难点 100% 需要新写**。你复用的是"脚手架"，不是"主体结构"。

## 五、开发成本估算

### 方案一：从 hub fork 自研

| 阶段 | 内容 | 人日 |
|---|---|---|
| P0 摸底 | 抓包复刻、确认 WAF 归属、PoW 复现、device_id 流程打通 | 2–4 |
| P1 上游客户端 | 登录/凭证刷新、会话创建销毁、PoW（wasm）、SSE 原始解析 | 4–7 |
| P2 OpenAI 适配层 | `messages`→`prompt` 扁平化、JSON-Patch 归约、SSE 重编码、非流式聚合 | 3–5 |
| P3 **工具调用** | prompt 注入 + 解析 + 三层修复管线 | **4–8** |
| P4 账号池与风控 | 节流、指数退避、封号探测、多账号轮转、代理出口 | 3–5 |
| P5 面板与运维 | 看板改造、API Key、用量统计、日志 | 2–3 |
| P6 联调稳定 | 压测、失效应对预案、文档 | 3–5 |
| **合计** | | **21–37 人日 ≈ 4–7 周（单人全职）** |

### 方案二：fork 现成 DeepSeek 专用代理（~~推荐~~ → 见第八、九章修正）

以 `deeperseeker`（Python，MIT）或 `DS-Free-API`（Rust，GPL-3.0）为基座，只做定制：

| 阶段 | 内容 | 人日 |
|---|---|---|
| P0 | 跑通上游 + 验证当前协议有效性 | 1–2 |
| P1 | 按需裁剪/加固（你的 agent 客户端要的字段、鉴权、限流策略） | 3–6 |
| P2 | 接自己的面板 / 用量统计（可复用 hub 的 `dashboard.html` 思路） | 2–4 |
| P3 | 联调 + 稳定性 | 2–3 |
| **合计** | | **8–15 人日 ≈ 1.5–3 周** |

> ⚠️ **修正**：第八章的封号实测表明，**这 8–15 人日大概率是沉没成本**——功能不是瓶颈，账号存活才是。此方案仅在你确认自己账号能撑住之后才成立。
>
> ⚠️ **许可证注意**：DS-Free-API 是 **GPL-3.0 且 README 明确「严禁商用」**。若涉及商业分发，优先考虑 **MIT 许可的 `deeperseeker`**。

### 方案三：只复用 hub 的"外壳"

把 hub 的通用设施（账号池 / API Key / 用量 / 面板 / 调度器）抽成一个**厂商无关的骨架**，再为 DeepSeek 写适配器。产出是一个"任意网页端 LLM → OpenAI"的通用框架。

- 工期：**25–40 人日**（比方案一还多，因为多了抽象层设计）
- 价值：如果未来还想接 Kimi / 通义 / GLM 网页端，这个投入才摊得平
- 判断：**这是另一个项目了**，不该挂在"接 DeepSeek"这个目标下做

### 运维成本（被普遍低估的部分）

- **网页端改版 = 随时失效**。社区经验：改版频率**从一周到一个月不等**。每次改版要重新抓包、改字段、回归测试。
- 这是**持续性的、不可预测的**成本。hub 场景下上游是官方 API（协议稳定），这里不是。
- 建议做法：把请求结构、字段名全部做成配置项；维护一个可重复的抓包流程；关注社区动态（通常改版后很快有人分享新抓包结果）。

## 六、经济账：为什么"省钱"这个理由不成立

### 官方 API 定价（2026-08-13 起，DeepSeek 官方文档）

| 模型 | 输入（缓存命中） | 输入（缓存未命中） | 输出 |
|---|---|---|---|
| **deepseek-v4-pro** | ¥0.025 / M | ¥3 / M | ¥6 / M |
| deepseek-flash（V4.1-Flash） | ~¥0.02 / M | ~¥1 / M | ~¥4 / M |

- 单次最大可处理 **100 万 token**，最大输出 **38.4 万 token**
- ⚠️ DeepSeek 已提示**近期计划大幅上调 API 整体价格**，方案未公布

### 算一笔 agent 任务的账

假设一次中等复杂度的 agent 任务：80 万 input（其中 90% 命中缓存）+ 3 万 output，走 v4-pro：

```
0.72M × ¥0.025  = ¥0.018   （缓存命中）
0.08M × ¥3      = ¥0.240   （缓存未命中）
0.03M × ¥6      = ¥0.180   （输出）
─────────────────────────
合计            ≈ ¥0.44 / 任务
```

**走 flash 再降一个数量级。**

也就是说：**每天跑 100 个 agent 任务，官方 API 成本约 ¥44（flash 更低）**。

### 对比

| | 网页端反代 | 官方 API |
|---|---|---|
| 直接费用 | ¥0 | ~¥44/天（100 任务，v4-pro） |
| 一次性开发 | 8–37 人日 | 0 |
| 持续运维 | 改版跟进 + 封号换号 | 0 |
| 稳定性 | 低（随时失效） | 高 |
| 工具调用 | prompt 模拟，不可靠 | 原生 |
| 并发 | 严格受限 | 按配额 |
| 合规 | ⚠️ 可能违反 ToS | ✅ |

**关键点**：WorkBuddy 场景的套利空间大，是因为上游是**订阅制打包**的（边际成本≈0，且账号是你自己的）。DeepSeek 网页端是**免费但消耗品**的账号，省下的是小钱，付出的是开发工时 + 封号风险 + 持续运维。

## 七、什么情况下**值得**做？

上面的结论有个前提：目标是"省 API 费"。但有几类动机是**成立**的：

1. **要体验灰度新模型**。网页端会先上 API 还没有的模型/能力。DS-Free-API 的 README 明确把"体验官方网页端灰度测试的最新模型"列为项目目的。如果你是为了这个，那它就不是省钱工具，而是**模型试鲜通道**。
2. **要网页端独有功能**。`search_enabled`（联网搜索）、`ref_file_ids`（文件上传）这些能力 API 侧形态不同。若你的 agent 需要"带联网搜索的对话"，网页端反代是唯一路径。
3. **个人学习 / 低并发自用**。一天几百次请求、单账号、串行调用，风险可控。这也是社区一致的建议定位。
4. **作为技术验证**，为将来的"通用网页端 → API 框架"探路。

**反之，如果你的目标就是"给 agent 客户端接一个便宜的 DeepSeek"——直接用官方 API。**

### ds-free-api 已实现的功能（超出预期）

- **端点齐全**：`/v1/chat/completions`、`/v1/responses`（含 `previous_response_id`）、`/v1/models`、`/anthropic/v1/messages`
- **工具调用**：三层自修复管道（文本修复 → JSON 修复 → 模型兜底），覆盖 10+ 异常格式，还处理全角 `｜`↔`|`、`▁`↔`_` 幻觉变体
- **深度思考默认开启**，`reasoning_effort: "none"` 可关；Anthropic 侧 `thinking → reasoning_effort`
- **文件上传**：内联 data URL 自动上传到 DeepSeek 会话；HTTP URL 自动触发搜索模式
- **超长提示词回退**：超限时自动分块补全 + 文件上传绕过
- **Web 管理面板 + PWA**，i18n（中/英/印尼）、账号池状态、API Key、请求日志、配置热重载
- **多账号池**：空闲最久优先轮转（DashMap 无锁读）
- **开箱即用**：提供 **macOS (aarch64/x86_64) 预编译包**，单可执行文件 + 单 TOML，默认端口 `22217`

### deeperseeker 更贴合 agent 场景

- **Context-Based Session Selector**：对规范化后的消息历史取 SHA-256 签名，**匹配并复用已有的网页会话**——这正好解决了我前面提的"有状态 vs 无状态"错配
- **Summarize-and-Rollover**：上下文逼近 ~393K token 时，让模型在草稿会话里生成交接摘要，开新会话续接
- **工具调用解析** DSML XML / `<tool_call>` XML / `<function_call>` / JSON → OpenAI / Anthropic schema
- 有 `CLAUDE_DESKTOP_SETUP.md`，支持 Claude Desktop / Claude Code
- 内置 `wasm/`（PoW 求解）
- **MIT 许可证**，且是 **Python**（与 hub 同栈，改造门槛低）

### 但是：真正的瓶颈不是功能，是账号存活

这是决定性的证据。issue #112（2026-09-18，标题《梁大人依旧精准封号》）：

> 目前该项目最新版本实测：**每个账号均使用不同 id**，且**每账号一共只发起 2 次请求**，每个请求收到完整回复后**在 6 至 10 秒左右才发下一个请求**，一共四个账号，目前其中一个账号 **10 分钟内被封**，另外两个 **12 小时内被封**，只有一个幸存。

**注意这个测试条件**：独立 `device_id`、每账号仅 2 次请求、6–10 秒人工间隔。这已经是最克制的用法了，仍然 4 个账号阵亡 3 个。

### 结构性矛盾：工具调用与规避封号互相冲突

`docs/deepseek-prompt-injection.md` 暴露了一个关键事实：

- 网页端后端会过滤全角 `<｜...｜>` 标签，作者改用 ASCII 变体 `<|tool▁calls▁begin|>` 才让模型遵循
- 而**这套 prompt 注入本身就是封号特征之一**。作者 2026-09 专门移除了"未闭合 `<think>` 注入 + 重复两遍的元指令 + 角色扮演式措辞"，理由是"消除这三个**容易被上游滥用检测命中的特征**（参见 issue #97 / #101 / #102 的封禁反馈）"

> **也就是说：agent 场景需要工具调用 → 工具调用需要 prompt 注入 → prompt 注入提高封号概率。**
> 这是一个**结构性矛盾**，不是靠工程优化能绕开的。越是把 agent 功能做扎实，越容易触发风控。

### 个人账号是否安全？——"共享账号才会被封"已被证伪

这是一个必须澄清的点，因为它决定风险等级。

**项目作者最初的解释是让人安心的**。README（2026-09）原文：

> 本仓库 README 与 issue 中历史公开的测试账号已全部失效（`USER_IS_BANNED` / `user is muted` / `RISK_DEVICE_DETECTED`）。**这不是项目 bug，而是上游针对共享账号的策略变化。**

按这个说法，风险来自"多人共用同一个账号"，用自己的号就没事。

**但这个假设被项目自己的测试推翻了。** issue #112 的测试条件恰恰是**非共享**的：4 个账号、各自独立 `device_id`、每账号仅 2 次请求、间隔 6–10 秒——仍然 3/4 被封。作者的"共享导致封号"理论在这里不成立。

**不过有一个重要保留**：#112 的账号是**为测试专门注册的，两个浏览器注册、注册时 IP 相同**。批量注册特征本身就是一个独立的风险因子，与"使用行为"无关。所以：

| 结论 | 置信度 |
|---|---|
| 共享账号必被封 | ✅ 已确证 |
| 批量注册的新号容易被封 | ✅ 已确证 |
| **长期正常使用的个人老号是否安全** | ❓ **无证据支持，不能假定安全** |

### 为什么个人账号的风险尤其值得在意

风控是**账号级**的，不是请求级的——一旦命中，损失的是账号本身，不是那一次请求：

| 后果 | 影响 |
|---|---|
| `biz_code=5 user is muted` | 临时禁言数周。**注意：这会连带影响你自己打开 `chat.deepseek.com` 正常使用**——不是只在 API 侧失效 |
| `biz_code=10 USER_IS_BANNED` | 永久封禁，不可恢复。**重新登录也无效** |
| `biz_code=11 RISK_DEVICE_DETECTED` | 缺设备指纹，补 `device_id` 可解 |

**而且你无法控制全部触发因素**：作者为降低命中率，专门移除了"未闭合 `<think>` 注入 + 重复元指令 + 角色扮演措辞"——说明 prompt 注入的特征本身就在风控模型里。你把 agent 功能做得越好，注入越重，越容易踩中。

**另外**：`device_id` 不可伪造，必须用真实浏览器登录一次才能取到。**如果你用主力账号去取 `device_id`，这个账号就已经进入了"可能被 API 调用"的链路。**

> 没找到任何证据表明**付费会员可以豁免风控**。若你的账号有价值（手机号实名、历史对话、可能还充了值），被永久封禁的代价远超省下的 API 费。

### 如果仍要试，如何把风险压到最低

1. **绝对不要用主力账号**。用一个可以随时丢弃的小号，且**不要用同一手机号关联的其他账号**（同人多账号可能被关联）。
2. **注册环境要干净**：独立 IP、独立浏览器 profile，避免批量注册特征。
3. **先让这个号"正常活一段时间"**：在网页端/App 真实用几天，积累正常行为历史，再考虑接 API。
4. **`device_id` 用该账号自己的浏览器取**，不要复用、不要伪造。
5. **控制频率**：参考 `deeperseeker` 的默认值——串行调用、请求间隔 ≥6–10 秒、每小时配额设到 10 次左右。
6. **先测再投入**：跑通后连续观察几天，确认账号状态稳定，再考虑要不要做二次开发。

> 即使做到以上全部，issue #112 的条件已经很接近这份清单了，结果仍是 3/4 阵亡。**请按"随时会封"的预期做决策。**

## 九、建议

### 结论已改变

原报告的建议是"若确要做，fork 现成项目"。**在看到封号实测数据后，这条建议要下调**：

| 目标 | 建议 |
|---|---|
| **体验 / 学习 / 摸协议** | ✅ 直接用 `ds-free-api` 的预编译包跑一遍，半小时的事，**不要写代码** |
| **个人偶尔用（单账号、串行、一天几十次）** | ⚠️ 可以试，但按"随时会封"预期，别把工作流依赖在上面 |
| **给 agent 客户端长期用** | ❌ **放弃**。issue #112 证明即使最克制的用法也保不住账号，而 agent 的调用强度远高于此 |
| **想基于它做二次开发** | 选 `deeperseeker`（MIT + Python + 会话复用），别选 `ds-free-api`（GPL-3.0 + 严禁商用 + Rust） |

### 推荐路径

```
第 1 步（30 分钟，零代码）
  └─ 下载 ds-free-api 的 macOS 预编译包，用自己的账号跑通一条消息
  └─ 亲手验证：能不能登录、能撑几次请求、什么时候开始 429 / 禁言
  └─ 这一步的信息量 > 前面所有调研

第 2 步
  ├─ 若你的账号撑不住（大概率）→ 到此为止，转官方 API
  └─ 若意外稳定 → 再评估要不要基于 deeperseeker 做定制

第 3 步
  └─ 无论哪条路，都不要投入 4–7 周自研
```

### 三条不要做的事

1. **不要自研**。功能已被完整实现，且这两个项目在工具调用、会话复用、PoW 上踩过的坑（标签格式、幻觉变体、切片 panic）你都要重踩一遍。
2. **不要从 hub fork 做这件事**。核心难点全部要新写，还要背 7,239 行单文件的改造负担。
3. **不要指望它跑 agent**。工具调用与规避封号在这个上游上是**结构性冲突**的，这不是投入工时能解决的问题。

### ⚠️ 许可证提醒

- `ds-free-api` 是 **GPL-3.0**，且 README 额外声明**「严禁商用」**——GPL-3.0 本身不禁止商用，这是作者叠加的额外限制，法律上效力存疑但意图明确。**商用直接排除。**
- `deeperseeker` 的 GitHub 元数据显示 `NOASSERTION`，但 **LICENSE 文件内容实为标准 MIT**——这是个好的信号，若做二次开发优先选它。

---

### 如果最终决定要做，先回答这三个问题

1. 你的 agent 客户端**是否强依赖原生 function calling**？（若是 → 直接放弃，网页端做不到可靠）
2. 你能提供**多少个真实 DeepSeek 账号**（含真实浏览器取 `device_id`）？寿命按 ~30–100 次请求/账号估，够撑多久？
3. 你能接受**每隔几周因为网页改版而停机维护**吗？
